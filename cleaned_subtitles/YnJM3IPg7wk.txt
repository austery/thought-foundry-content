CPU其实很闲 论文里的数据显示 大约90%的容器和微虚拟机沙盒 平均CPU使用率不到申请量的5% 这就意味着CPU超售是天然可行的 生产环境里 单个节点能稳定跑3200个容器或者800个微虚拟机 但超售不是没有代价的 内存效率和CPU干扰问题会变得越来越突出 第三个，有状态而且生命周期长 Agent会修改文件、安装依赖、启动服务 后面的操作都依赖这些累积的状态 一个沙盒可能要撑过很多轮交互 Agent可能会搞坏文件系统、耗尽资源、干扰系统组件 影响rollout的正常进行 甚至波及同节点的其他任务 第七个，可中断性 GPU训练任务经常被抢占 但rollout可能还在跑 平台得能保住执行状态 支持高效恢复 这七个特点叠加在一起 就决定了DSec不能是一个简单的沙盒运行时 它必须是一个完整的弹性执行平台 那具体该怎么实现的 咱们一层一层说 先讲最上层的用户接口和四种沙盒后端 用户通过libdsec这个Python客户端库来访问DSec 你指定沙盒类型、镜像ID、CPU内存限制、生命周期策略、网络规则 以及初始用户 就能创建一个沙盒 然后在里面执行shell命令或者工具调用 拿到输出和返回状态 四种后端虽然内部差别很大 但是用户看到的生命周期是统一的 哪四种呢？ 最轻的是FnCall 面向短任务、无状态的场景 比如刷题、代码编译、serverless程序、GPU算子评测 FnCall跑在预先创建好的容器里 避免每次调用都重新配置 值得一提的是GPU版本的FnCall 它有两种模式 共享模式下多个容器共用一块GPU 适合轻量任务提高利用率 独占模式下一个容器占一块GPU实例 给性能敏感的任务用 具体实现上用了NVIDIA的MIG技术 把GPU切成隔离的实例 编译这类工作交给CPU版的FnCall处理 还提前预热了一批Python进程池 减少启动开销 第二种是容器 这是软件工程和通用工具调用任务的主力后端 启动快、密度高 能跑绝大多数Linux软件栈 缺点是共享宿主机内核 安全敏感任务不太适合 第三种是Firecracker微虚拟机 隔离性更强 同时保持Linux兼容性 适合安全敏感任务、需要更强租户隔离的场景 代价是内存开销更高 启动也比容器慢 第四种是完整虚拟机 覆盖需要完整商用操作系统环境的工作负载 比如通过QEMU跑安卓虚拟机 还有需要GUI或图形渲染的任务 这类资源开销最高 但是有些依赖特定OS API、移动端运行时 或者完整系统执行的任务，非它不可 这四种后端各有各的位置 生产环境里 容器和微虚拟机占了实例数和资源消耗的大头 FnCall用少量常驻环境服务大量轻量调用 完整VM覆盖那些比较特殊但又很重要的场景 接下来聊聊平台的整体架构 一个请求从SDK发出来到沙盒跑起来 中间要经过哪些组件 DSec在架构上分两大块 集群级服务和沙盒运行时 集群级服务管接入和跨节点调度 包括IAM、API Server、Placement Engine和Watcher IAM负责身份认证和权限管理 DSec的IAM有个特点 支持多级项目嵌套 而不是常见的扁平或两级结构 授权的主体，包括Agent和harness 可以创建子项目 从父项目分一部分配额出去 再授予子项目里的管理权限 人和Agent用的是同一套管理API和授权模型 API Server是整个沙盒集群的入口代理 训练和评测代码在受信任的GPU服务器上调用libdsec 而沙盒里跑的是模型生成的不可信代码 两边网络是隔离的 API Server是唯一允许的通信路径 它本身不存沙盒状态 沙盒ID里编码了所属的edge节点 所以任何一个API Server实例 都能直接把请求转发到目标节点 入口层可以水平扩展 Placement Engine负责给每个新沙盒选宿主节点 分两步走，先过滤 只保留健康的、具备所需后端和硬件能力的节点 然后再排序，从合格节点里随机抽几个 选负载最低的那个 这个算法叫power-of-k-choices 能有效避免羊群效应 减少突发RL环境 在setup和工具调用阶段的互相干扰 Watcher负责监控整个集群的健康状态和负载信息 Placement Engine的决策准不准 全看Watcher收集的数据 Watcher会定期探测每个edge和宿主机的健康状况 收集各种调度相关的状态数据 有意思的是 Placement Engine和Watcher都不需要持久化状态 Placement Engine不保存沙盒的执行状态 Watcher重启后重新poll一遍edge 就能重建集群视图 所以这两个组件加实例或者换实例都很方便 不需要走复杂的恢复流程 然后是节点上的沙盒运行时 包括Edge、Aether和Chronus 底层靠3FS存镜像数据 每个节点跑一个Edge 处理API Server发过来的创建请求 接请求之前先查本地容量 不够就直接拒掉 这个节点级的准入检查 是对Placement Engine调度决策的补充 毕竟调度器用的是定期刷新的集群状态 可能有延迟 创建的时候 Edge负责配置存储、应用eBPF网络策略、启动运行时 这里还补充一个细节 FnCall和容器不是直接跑在裸机上的 而是跑在QEMU/libvirt虚拟机里面 这个虚拟机提供了一个隔离的内核和网络栈 在不可信容器和裸金属之间多加了一层安全边界 对于图形密集型的工作负载 比如电脑操作的GUI应用、浏览器、游戏、3D渲染 还用到了宿主机hypervisor的半虚拟化GPU接口 比如virtio-gpu 容器和虚拟机沙盒里还跑着Aether和Chronus Aether是一个跨平台代理 跟Edge建立通信通道 容器用Unix domain socket 虚拟机用vsock 每次操作，Aether根据终端会话ID 找到或创建对应的Chronus实例 然后把操作转发过去 Chronus提供沙盒内部的shell会话抽象 每个实例代表一个独立的shell会话 支持命令执行、文件系统操作、HTTP请求和流式I/O 同一个沙盒里可以并发跑多个Chronus实例 镜像数据存在3FS上 也就是Fire-Flyer File System 这是DeepSeek自己的分布式文件系统 3FS的硬件配置也挺猛的 每个存储服务器配20块15TB的SSD 两块400Gbps的RDMA网卡 几十台存储服务器就能支撑几十万CPU核集群的按需镜像加载 讲完架构 再说说几个核心的技术机制 这些才是论文里最有干货的部分 我们先讲可组合环境层 刚才说了 一个沙盒的环境可以拆成三部分 基础镜像提供OS级依赖 工作区带任务的代码库和特定依赖 还有一个或多个频繁更新的工具包 比如DeepSeek Harness 如果把这三部分打成一个完整镜像 维护成本会非常高 假设M个基础镜像、N个工作区、K个工具包 更新m个基础镜像 就要重新构建O(m·N)个组合镜像 更新k个工具包就是O(k·N)的成本 DSec的思路是把这三层各自独立版本化 沙盒启动的时候再用overlayfs组合起来 基础镜像在最底下 工作区作为只读层插在上面 每个工具包再往上叠 overlayfs本身就支持多个只读下层目录堆叠 在内核中呈现一个统一的目录树 冲突按优先级来 最上面还有个可写的上层目录 接住所有的运行时写入 这样一来，更新m个基础镜像 就只需要重建m个基础层 工作区和工具包都不用动 更新k个工具包也只需要重建k个工具包层 维护成本直接从O(m·N)和O(k·N)降到了O(m)和O(k)。 而且这些发布出去的环境层都是不可变的 所以用EROFS文件系统来存 EROFS是专门为只读数据设计的 比ext4、XFS这些可写文件系统 少了写相关的bookkeeping 磁盘布局更紧凑 还支持数据压缩同时保持随机访问 跟tar.gz不一样 EROFS可以只读需要的压缩块 不用把整个镜像都传下来解压完才能用 微虚拟机那边也是类似的可组合层模型 基础镜像和工具包打成独立版本的EROFS镜像 作为只读块设备暴露给客户机 客户机里的根文件系统用overlayfs 挂载的EROFS文件系统作为下层 可写磁盘上的ext4目录作为上层 除了环境怎么组合 镜像怎么分发也是个大问题 这就是按需加载要解决的事 论文里有个数据很关键 沙盒运行时实际访问的数据 只占完整镜像的很小一部分 不同编程语言的容器镜像 运行时访问比例从4.2%到13.3%不等 JavaScript镜像最低，只有4.2% Go最高，也才13.3% 既然大部分数据根本用不上 全量拉取就特别浪费 DSec把镜像数据放3FS上 运行时按需读取 但是3FS有个特点 大块连续读写性能很好 小块随机I/O表现不行 所以设计上做了三个针对性的处理 第一，写入全部本地化 沙盒的写入操作都是不规则且不可控的 比如日志文件这种小而频繁的写 可写层直接放在节点本地磁盘上 完全避开3FS的小写 penalty 第二，读取按需而且走大块 只读镜像数据只有在被访问的时候才从3FS取 而且I/O尽量凑成大块来做 利用3FS对大I/O请求的高吞吐能力 第三，元数据尽量放本地 文件系统元数据经常是小读取 EROFS有个多设备模式 可以把文件系统元数据和文件数据分开 DSec把EROFS元数据下载到worker的本地磁盘 文件数据留在3FS上 这样元数据遍历和路径查找就不会产生远程I/O 效果怎么样呢？ 论文里做了实验 8192个容器同时突发部署 按需EROFS加载跟全量本地缓存的性能差不多 35分钟左右全部完成 用Docker冷拉取要超过60分钟 慢了1.71倍 磁盘写入量方面，按需加载大概700GB Docker冷拉取超过1600GB，减少了57% 还有一个对比是EROFS直接挂载跟传统tar.gz解压的对比 同样的评测工作区和工具包，用tar.gz的方式每个沙盒都要解压一遍 端到端任务完成时间要79分钟 磁盘写入总量是EROFS的5.5倍 峰值写入吞吐是3.4倍 EROFS直接挂载共享层，不用解压 45分钟就完成了，快了1.76倍 接下来讲高密度资源管理 这部分是内存和CPU的优化 先来说内存 微虚拟机的内存浪费有两个来源 一是镜像数据通过虚拟块设备读取 宿主机缓存一份 客户机又缓存一份，两边重复了 二是客户机里的空闲页面不会主动还给宿主机 申请的内存经常比实际需求大 客户机内部没什么内存压力 自然也就不会去回收不活跃的页面 这里DSec用了两套互补的机制来解决 一套是virtio-pmem加DAX 它把文件访问直接映射到宿主机的页面 不需要再拷贝到客户机的RAM里 这样同节点上的多个微虚拟机 可以共享同一份宿主机页缓存 效果是峰值内存使用量减少了40.2%。 但virtio-pmem也不是万能的 冷访问的时候需要同步缺页处理来建立映射 而且客户机得为整个pmem设备的地址范围 分配page结构的元数据 如果按照4KB页面、64字节page结构的话 元数据就要占pmem容量的1/64 128GB的pmem设备就需要2GB的客户机RAM来存元数据 另一套是DAMON加virtio-balloon的空闲页报告 DAMON是Linux里一个基于采样的内存访问监控框架 定期采样页访问位 找出冷的文件页面 通过内核回收路径把它们驱逐出去 回收之后 零散的页面回到伙伴分配器 合并成高阶块 满足空闲页报告的要求 virtio-balloon驱动会再把这些空闲页主动报告给宿主机hypervisor 宿主机通过madvise释放对应的内存 这套机制单独用的话 峰值内存变化不大 但是时间积分的内存消耗减少了21.2%， 而且CPU开销不明显 生产环境里 只读的EROFS基础镜像层和工具包层用virtio-pmem加DAX 比较大的可写磁盘 用DAMON加balloon空闲页回收 两者配合效果最好 然后是CPU的QoS调度 超售的时候 怎么保证延迟敏感的任务 不受尽力而为任务的干扰呢？ DSec把沙盒分成两类 延迟敏感的LS类和尽力而为的BE类 BE类沙盒放在SCHED_IDLE调度优先级下 只要有LS任务要跑 它们就让出CPU 但是光有调度优先级还不够 因为同一个物理核的两个SMT兄弟线程 是共享执行资源的
